Front-End vs Back-End

Até agora, tudo o que você escreveu rodava dentro do navegador do usuário. A partir de hoje, vamos escrever código que roda em outro computador, longe dele.

Front-End

  • Roda no navegador (Chrome, Firefox…).
  • HTML, CSS e JavaScript.
  • Cuida do que o usuário vê e clica.
  • O usuário pode ver todo o código: basta apertar F12.

Back-End

  • Roda em um servidor.
  • Java, banco de dados, regras do negócio.
  • Cuida de guardar, buscar e conferir os dados.
  • O usuário nunca vê o código. Só vê a resposta.

No seu SeuNomeFlix, a lista de filmes está escrita à mão dentro do HTML. Quando o curso terminar, ela virá de um banco de dados de verdade — e para trocar um filme você não vai precisar mexer em uma linha de HTML.

O ciclo requisição-resposta

A web inteira funciona em um vaivém muito simples: alguém pede, alguém responde. Esse pedido se chama requisição e a devolução se chama resposta.

Cliente

O navegador do usuário

requisição

resposta

Servidor

O nosso programa em Java

O servidor nunca começa a conversa. Ele fica parado, esperando. Se ninguém pedir nada, ele não faz nada. Guarde isso: é a diferença mais importante entre o que você fazia antes e o que vai fazer agora.

Anatomia de uma URL

Toda requisição começa em um endereço. Clique em cada pedaço abaixo para descobrir o que ele faz:

https://seunomeflix.com/filmes/42?genero=acao&ano=2024

Aquele ? deve parecer familiar: é exatamente o que apareceu na barra de endereços quando vocês enviaram um formulário com method="get".

Métodos HTTP

Além do endereço, toda requisição carrega um método: o verbo que diz qual é a intenção do pedido.

  • GET — quero ver alguma coisa. Buscar a lista de filmes.
  • POST — quero criar alguma coisa. Cadastrar um filme novo.
  • PUT — quero alterar alguma coisa. Corrigir a nota de um filme.
  • DELETE — quero apagar alguma coisa. Tirar um filme do catálogo.

Vocês já usaram dois deles sem saber: GET e POST são os valores do atributo method do <form>.

GET    /filmes        → lista todos
GET    /filmes/42     → mostra o filme 42
POST   /filmes        → cadastra um novo
PUT    /filmes/42     → altera o filme 42
DELETE /filmes/42     → apaga o filme 42

Repare: o endereço é quase sempre o mesmo. O que muda é o verbo.

Códigos de status

Toda resposta vem com um número de três dígitos que resume o que aconteceu. O primeiro dígito já conta a história:

  • 2xx — deu certo.
  • 3xx — mudou de endereço, procure em outro lugar.
  • 4xx — o cliente errou (pediu o que não existe, esqueceu um dado).
  • 5xx — o servidor errou (o código quebrou, o banco caiu).
200 201 301 400 401 404 500

200 OK — deu tudo certo e a resposta está aí. É o código mais comum da web.

⚠️ Cuidado: nunca confie no cliente

Validação no front-end não é segurança

Lembra do required e do min/max que vocês usaram nos formulários? Eles são ótimos para ajudar o usuário — mas não protegem nada.

Qualquer pessoa pode abrir o F12, apagar o atributo required e enviar o formulário vazio. Ou enviar a requisição direto, sem passar pela sua página. O navegador é o computador dela, não o seu: ela manda no que acontece lá.

Por isso a regra número um do back-end: tudo o que chega no servidor precisa ser conferido de novo, no servidor. Validar no front é conveniência; validar no back é obrigação.
