Relacionamentos: Ligando Tabelas e Fazendo Consultas Próprias

Da entidade isolada para a Agência de Espiões com JOIN.

Role para baixo para começar

1. Relacionando Entidades: @ManyToOne

Na aula de comunicação total (aula passada) cada entidade vivia sozinha. No banco, porém, as tabelas se ligam por chaves estrangeiras: todo espião pertence a uma agência. No Java, em vez de guardar só o número da chave, guardamos o objeto inteiro.

  • @ManyToOne: "muitos espiões para uma agência". Descreve a relação.
  • @JoinColumn(name = "id_agencia"): qual coluna da tabela Espiao guarda a chave estrangeira. O nome é o da coluna no MySQL, não o do atributo Java.
  • nullable = false espelha o NOT NULL do schema. A missão aceita NULL, então fica sem isso.
@Entity
public class Espiao {
    // id, nomeReal, nomeEspiao...

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "id_agencia", nullable = false)
    private Agencia agencia;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "id_missao")
    private Missao missao;
}

Sem import: Agencia e Missao estão no mesmo pacote (model), então o Java as enxerga sem import. As anotações vêm do jakarta.persistence.*.

2. Quando Buscar? LAZY x EAGER

O atributo fetch controla quando o Hibernate carrega o objeto relacionado.

LAZY (preguiçoso): ao carregar o espião, a agência não vem junto. O Hibernate coloca um substituto (proxy) e só vai ao banco quando você usa, por exemplo em getAgencia().getNomeAgencia().

EAGER (ansioso): traz o objeto relacionado junto, sempre. É o padrão do @ManyToOne.

O risco: problema N+1. Para listar 3 espiões e a agência de cada um, o Hibernate pode fazer 1 consulta pela lista e mais 1 para cada agência. Com 1000 espiões, são 1001 idas ao banco.

Dica: ligue spring.jpa.show-sql=true no application.properties e conte os select no console. Ver as consultas aparecendo ensina mais do que qualquer explicação.

3. Consulta Própria: @Query, JPQL e JOIN FETCH

Antes, o controller buscava a agência e depois os espiões: duas idas ao banco. Agora o repository faz tudo em uma só, escrevendo a consulta com @Query.

@Query("SELECT e FROM Espiao e JOIN FETCH e.agencia a WHERE a.nomeAgencia = :nomeAgencia")
List<Espiao> buscarPorNomeAgencia(@Param("nomeAgencia") String nomeAgencia);
  • JPQL parece SQL, mas usa classes e atributos Java: Espiao, e.agencia, a.nomeAgencia. Não existem tabelas nem colunas aqui, por isso SELECT e devolve objetos Espiao inteiros.
  • JOIN FETCH: faz o JOIN e já preenche o campo agencia de cada espião, na mesma consulta. Um JOIN simples só filtra, e a agência seria buscada depois.
  • :nomeAgencia é um parâmetro nomeado, e o @Param liga esse nome ao argumento do método. O valor viaja separado do texto, o que evita SQL Injection.

Nome do método: com @Query, o Spring executa o texto e ignora o nome. Sem @Query, ele lê o nome (findByNomeAgencia vira SQL sozinho). O JOIN FETCH só trouxe a agência: a missão (LAZY) ainda gera selects extras no console, e dá para resolver com LEFT JOIN FETCH e.missao.

4. SQL de Verdade: nativeQuery e LEFT JOIN

Para exibir só nome_espiao | agencia | missao não precisamos de objetos, só de três colunas. Aqui escrevemos SQL puro e recebemos o resultado em uma interface com getters (uma "projeção").

public interface EspiaoResumo {
    String getNomeEspiao();
    String getAgencia();
    String getMissao();
}
@Query(nativeQuery = true, value =
  "SELECT e.nome_espiao AS nomeEspiao, " +
  "       a.nome_agencia AS agencia, " +
  "       m.nome_missao AS missao " +
  "FROM Espiao e " +
  "JOIN Agencia a ON a.id_agencia = e.id_agencia " +
  "LEFT JOIN Missao m ON m.id_missao = e.id_missao " +
  "WHERE e.id_espiao = :idEspiao")
EspiaoResumo buscarResumoPorId(@Param("idEspiao") Integer idEspiao);
  • nativeQuery = true: o texto é SQL do MySQL, com nomes de tabelas e colunas.
  • AS nomeEspiao: o apelido precisa casar com o getter (getNomeEspiao). Assim o Spring sabe qual coluna vai em qual getter.
  • JOIN descarta linhas sem par. LEFT JOIN mantém todos os espiões, e a missão vem NULL quando não existe.

JPQL ou nativa? JPQL quando você quer objetos (Espiao com agencia preenchida). SQL nativo quando você quer colunas prontas para exibir.

5. No Controller: NULL, 404 e CORS

@GetMapping("/espioes/resumo")
public ResponseEntity<String> buscarResumo(@RequestParam Integer id) {
    EspiaoResumo r = espiaoRepository.buscarResumoPorId(id);

    if (r == null) {
        return ResponseEntity.notFound().build();
    }

    String missao = r.getMissao() == null ? "não há missão" : r.getMissao();
    return ResponseEntity.ok(r.getNomeEspiao() + " |
     " + r.getAgencia() + " | " + missao);
}
  • @RequestParam: lê o valor da query string, ex.: /espioes/resumo?id=1. Na aula de comunicação total, o @PathVariable lia da própria URL (/jogos/3).
  • null: o NULL do banco chega ao Java como null, e o ternário ? : troca por um texto. Poderia ser feito no front, ou no banco com COALESCE.
  • 404: id inexistente devolve notFound(), e o front trata !resposta.ok.

CORS: o erro que aparece no front

O navegador bloqueia um site que chama outro endereço (outra origem), a menos que o back-end autorize com @CrossOrigin na classe do controller. Ao abrir o HTML direto do disco (file:///), a origem é null e o bloqueio também vale. Quando o @CrossOrigin some, o back-end responde 200 e mesmo assim o console mostra erro de CORS.
